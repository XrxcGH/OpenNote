# ADR 0010: Interface components, state, and structure

- Status: Proposed
- Date: 2026-09-30

## Context

Phase 2 builds the app shell that every later phase extends: the title bar, command bar, navigation tree, palette, settings, setup, and the overlays they use. DEVELOPMENT.md chose React and TypeScript in architecture decision record (ADR) 0001, but not how components, state, and structure work inside them. The forces:

- **Accessibility:** docs/BRAND.md section 12 requires the Web Content Accessibility Guidelines (WCAG) 2.2 at level AA, the level most accessibility laws require. It also requires Narrator and NonVisual Desktop Access (NVDA) support, and full keyboard use. The navigation tree is the most-used control.
- **Performance:** the window must appear within 1 s, and any input must show a response within 50 ms on the reference laptop, with a 1,000-page notebook. Start-up JavaScript grows with every phase.
- **Brand:** every visual value comes from tokens, and the CHECKS `brand-consistency` rule enforces it.
- **Contributors:** 14 phases, many contributors, and parallel work on separate branches.
- **Testing:** Playwright and component tests must run the real interface without Rust.

## Decision

We will build the interface from about 25 hand-written components in `app/src/ui/`. Each follows its pattern in the Accessible Rich Internet Applications (ARIA) Authoring Practices Guide (APG) of the Web Accessibility Initiative (WAI). Each uses tokens only, and is tested against its pattern's key table, with React Aria's behavior as the reference for edge cases. We will not adopt a UI kit.

We will hold state in a small external store on React's `useSyncExternalStore`, one store per slice, read through selectors. Its API mirrors Zustand's, so a later switch would be mechanical. Navigation is a typed `Location` value with back and forward history, not a router.

We will structure the code around:

- a `Platform` interface with a Tauri and a web implementation, where only `platform/tauri/` may import `@tauri-apps/api`;
- eight registries (commands, command bar, context menus, settings sections, setup steps, title bar items, palette providers, and before-exit hooks), filled by each feature's `register.ts`;
- ESLint import boundaries: features talk through their `index.ts`, and `ui/` never imports state, services, or features;
- CSS Modules with cascade layers and logical properties; no styles written in JavaScript and no utility framework;
- types shared with Rust generated by ts-rs 12.0.1 in `cargo test` (development only), with a drift check in CI.

The runtime npm dependencies don't change. The start-up JavaScript budget is 125 KB gzipped, checked on every pull request.

## Options considered

| Option | For | Against |
|---|---|---|
| Hand-written APG components and our own store (chosen) | No new runtime dependency; exact control of tokens, motion, and ARIA; `role="tree"` with flat rows; the smallest bundle; stores usable outside React | About 25 accessibility-critical components to own; each needs thorough key-table tests |
| React Aria Components 1.21 with Zustand 5 | Well-tested focus management, collections, drag and drop, and virtualization; familiar to many contributors | Its tree is a `treegrid`, which Narrator and NVDA read less naturally; its toast API is unstable; start-up JavaScript around 220 KB gzipped, nearly twice the chosen budget |
| Radix primitives with dnd-kit, cmdk, and TanStack Virtual | Popular pieces | No tree; four libraries with four focus models |
| React context and `useReducer` for state | Built in | Every consumer re-renders on each change; can't be used from commands or Rust event handlers outside React |
| Redux Toolkit | Conventions and developer tools | About 12 KB and much more code per feature; its developer tools don't work inside WebView2 |
| Zustand 5 alone | 1 KB, well known | Replaces 60 lines we can own; kept as the documented fallback |

## Consequences

- Easier: tokens, motion, and ARIA are fully ours, and screen reader behavior is predictable. Start-up stays small. The whole interface runs in a browser for Playwright and for contributors without Rust, and later phases add features by registering them.
- Harder: we own the accessibility of every widget. The mitigations are component tests in a real browser with a key-table section per component, and axe in every test. ARIA snapshots, the focus walk, a nightly NVDA canary, and the manual Narrator and NVDA checklist at each phase exit add to them.
- Follow-up work: the ESLint rules, the registries' consistency test, the coverage test that every exported component has a test file, and the development gallery.
- Revisit if the widget code grows past what reviewers can keep accessible, for example when a later phase needs a data grid or virtualized collections with complex focus. Also revisit if React Aria ships a `role="tree"` and a stable toast with a much smaller footprint. The owners of Phase 7 (tables) and Phase 8 (search) should check.
